## The idea

Detect muscle groups from video and turn that into something a machine acts on. The
detection is a YOLO-family model; the interesting half is everything after training,
because a model that scores well in a notebook and a model that keeps a robot arm
responsive are two different artefacts.

This was a personal project, built to practise the deployment path end to end on
hardware I could hold: a Jetson Nano B01 with an OV5647 camera and an arm on the desk.

  ### Why the conversion is the work

  Exporting to ONNX is where most of the surprises live. Operators that PyTorch resolves
  at runtime have to become static graph nodes; the opset version decides whether an op
  exports cleanly or turns into a slow decomposition; and getting the dynamic axes wrong
  means an engine that only accepts one batch size and one resolution.

  TensorRT then compiles that graph **for the specific device it will run on**. It fuses
  layers, picks kernels by benchmarking them, and drops to FP16 where the accuracy loss
  is acceptable. The engine file is not portable — build it on the Jetson, not on the
  workstation.

  The payoff was roughly **30% lower inference latency** than the unoptimised path, which
  is the difference between an arm that tracks and an arm that lags behind what it is
  looking at.

## What I took from it

The Hailo work and this project attack the same problem from two vendors. Hailo compiles
to `.hef` and TensorRT compiles to `.plan`, but the shape of the job is identical:
get the graph out of the training framework cleanly, understand what the compiler is
allowed to change, and verify accuracy *after* conversion rather than trusting it.

Having done both means I read a new accelerator's SDK looking for the same three things
rather than starting over.
