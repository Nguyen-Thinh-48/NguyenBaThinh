## The problem

Access control systems that send faces to a server have two problems: they stop
working when the network does, and they move biometric data off-site. The brief was a
terminal that recognises a face, decides locally, and only talks to a server to record
that it happened.

The hardware budget was a Raspberry Pi 5 with a Hailo-8L M.2 accelerator — roughly
5&nbsp;W for the inference. The target was real-time: a face recognised while the
person is still walking up to the door, not after they have stopped and waited.

  ### Everything happens on the box

  Detection uses **SCRFD-500m**, which returns a bounding box and five landmarks in one
  pass. The landmarks matter as much as the box: the two eye points give the rotation
  needed to straighten the face before embedding, and straightening it is worth more
  accuracy than most model changes.

  Embeddings come from **MobileFaceNet** trained on ArcFace data, producing a
  512-dimension vector per face. Matching is plain cosine similarity against the stored
  vectors, thresholded at 0.7.

  Both models are compiled to Hailo's **HEF** format and executed through HailoRT. The
  Pi's CPU is left to do capture, alignment and the Qt interface.
</MediaSplit>

## Pruning that made the model more accurate

The interesting result was not the speed-up — it was that removing a fifth of the
network made it better.

The idea: inside a trained convolutional layer, many filters end up nearly parallel to
each other. They cost compute and contribute almost nothing new. I measured pairwise
**cosine similarity between filters** and removed those above a 0.3 similarity
threshold as redundant.

| MobileFaceNet | Parameters | Accuracy |
| --- | --- | --- |
| Original | 1.778 M | 89.42% |
| Structurally pruned (cosine, threshold 0.3) | **1.417 M** | **95.82%** |

A 20% smaller network scoring 6.4 points higher is not magic — it is the redundant
filters having acted as noise on the embedding. Cutting them tightened the clusters
that cosine similarity has to separate.

The honest caveat: in the current implementation the pruned filters are zeroed rather
than physically removed from the graph, so the parameter count is the logical one. Doing
the structural removal properly would recover the memory too, and it is the first item
on the list if I return to this.

## What the accelerator actually bought

Both models were benchmarked as ONNX on the Pi's CPU and as HEF on the Hailo-8L:

| Model | Format | Size | Time per image |
| --- | --- | --- | --- |
| SCRFD-500m | ONNX | 2.5 MB | 79.52 ms |
| SCRFD-500m | **HEF (Hailo)** | 5.5 MB | **31.43 ms** |
| MobileFaceNet | ONNX | 8.2 MB | 22.39 ms |
| MobileFaceNet | **HEF (Hailo)** | 6.4 MB | **8.76 ms** |

Detection got 2.5× faster and embedding 2.6× faster. Note the HEF file for SCRFD is
*larger* than the ONNX — the compiled format trades disk for a layout the accelerator
can stream, which is the trade you want on a device with an SD card and a power budget.

Together with the pruning, that is what put the running system at roughly **25 FPS**.

  ### Two cameras, one identity

  The second camera is the part that came from the research side of this project.
  Rather than using stereo purely for depth, both views run the full pipeline and their
  512-d embeddings are combined by **late fusion** before matching.

  Two views of the same face disagree in useful ways — a partial occlusion, a harsh
  side light or an unflattering angle rarely hits both sensors identically. Fusing
  after the embedding rather than before means each branch stays a clean face vector,
  and the fusion just picks up the consensus.

  Registration uses the same idea over time instead of space: several frames are
  captured, blurry and noisy ones are filtered out, and the stored vector is the average
  of what survives.
</MediaSplit>

## Anti-spoofing without a second model

A printed photo passes face recognition perfectly. The usual fix is another neural
network, which there was no compute budget for.

Instead the system watches the landmarks it is already computing. Over a window of at
least 30 frames it tracks their **velocity, variance and geometric deformation**. A
real face is never still — micro-movements, breathing, small head rotations — and it
deforms non-rigidly. A photo, a phone screen or a replayed video moves as a flat plane
or does not move at all.

It costs almost nothing on top of detection, because the landmarks are free at that
point, and it catches printed photos, screen replays and simple deepfake playback.

## Making it a product, not a demo

The parts that are unglamorous but decide whether something ships:

- **OTA updates** — the terminal compares its commit hash against GitHub, backs itself up
  and updates in place. Nobody carries an SD card to an installed door.
- **A Go REST API** for users, check-ins and attendance history, with a small web admin
  interface, so the terminal is not also the database.
- **A PyQt5 touch interface** for registration, the user list, Wi-Fi setup and admin login.
- **Thermal monitoring**, because a Pi 5 with an M.2 accelerator in a sealed enclosure will
  throttle, and you want to know before the FPS quietly halves.
